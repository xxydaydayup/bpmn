# 流程控制面与 Camunda 7 引擎验证边界

**Status: accepted**

流程工作台定位为面向流程管理员和运维人员的流程控制面，负责流程定义发布、运行实例监控、历史查询和受控运维；普通业务用户的审批、表单填写和业务决定由未来业务系统通过 Go API 完成。工作台保留独立的“引擎验证中心”，用于在没有业务系统时验证 Camunda 7 的部署、启动、任务流转、历史记录和异常行为，但验证场景不代表真实业务审批已经可用。

当前目标引擎契约按已确认的 Camunda Platform REST API 7.20.0 约束。开发阶段可以通过 Vite 代理直连 Camunda REST；生产阶段由 Go 服务承接认证、租户、权限、变量校验、幂等、错误适配和操作审计，浏览器不得持有 Camunda 管理员凭据。

## 决策

- 工作台首期按 Camunda 原生对象组织：部署、流程定义版本、流程实例、人工任务、历史、Job、Incident 和 External Task。
- 工作台首期提供查询和图形监控，并提供暂停/恢复和受控 Job 重试等有限运维动作；实例终止、级联删除、执行路径修改、迁移和批量操作后置，并要求权限、原因、二次确认和审计。
- 普通业务审批动作不在工作台实现。工作台不把裸 `complete` 作为业务审批契约；未来业务系统通过 Go API 提交同意、拒绝、退回等业务决定。
- 引擎验证场景使用唯一测试部署、固定变量和显式断言，验证完成后默认级联清理；失败时允许保留部署和实例用于排查。
- 短期设计稿由 BPMN 文件和 Git/人工目录管理，不使用浏览器本地缓存作为事实来源，也不把 Camunda 引擎导出的 XML 反向覆盖设计稿。正式发布需要关联设计稿内容哈希、发布人、环境、deploymentId、processDefinitionId 和版本号；后续可由 Go 服务或对象存储承接版本保存。
- Camunda 的 `camunda:historyTimeToLive` 是部署成功的引擎前置条件，由平台策略统一校验或注入；它只控制引擎历史清理，不代替业务审计保留。
- 新版本发布后，旧实例继续使用原 `definitionId`；新实例默认使用最新激活版本。首期不提供流程实例迁移。
- 验证环境优先使用 FULL history level；正式环境先使用 FULL 与明确的 `historyTimeToLive`，变量默认脱敏，业务审计独立保存并不依赖 Camunda 历史。
- 部署、启动和任务决定等写操作使用幂等键；请求超时后先查询真实结果再决定是否重试。
- 第一批稳定验证场景为串行审批和金额分支；并行、多实例、会签、或签和退回重提先作为独立的引擎能力验证，待业务语义确定后再进入正式模板。

## Considered Options

- **把工作台做成业务审批应用：** 可以较早演示完整流程，但会把表单、人员、意见、业务数据和引擎运维耦合在一起；在业务系统尚未确定时容易形成临时且不可复用的审批协议。
- **只做 Camunda REST 管理页面：** 能快速覆盖接口，但会暴露引擎凭据、版本字段、分页和变量协议，无法承担正式权限、租户、幂等和审计责任。
- **只依赖 Camunda 保存设计稿：** 可以减少一个存储接口，但无法稳定保存设计器布局、原始扩展和发布前版本，也不利于跨环境推广、差异比较和回滚。
- **不做引擎验证：** 页面可以查询部署结果，却无法在业务系统出现前验证条件分支、任务流转、历史记录和异常行为。

采用控制面 + 引擎验证中心 + Go 包装层的组合，在当前没有业务系统时保持可验证性，同时为后续业务系统接入保留清晰边界。

## Consequences

- 前端需要把正式部署和验证部署区分展示，记录环境、来源、内容哈希和清理状态。
- 实例详情必须按实例所属的 `definitionId/version` 读取 BPMN 图，不能使用当前最新设计稿解释旧实例。
- 运行监控需要合并当前活动树与历史活动；活动树本身不是完整执行轨迹。
- Go API 需要提供统一的分页、错误、幂等、租户和审计语义，并把 Camunda 7.20.0 的偏移分页和变量格式适配到前端。
- 设计稿版本服务可以后置，但正式发布流程必须保留可追溯的 XML 原文或内容哈希；临时验证场景可以只由仓库模板和本地导出文件支持。
- 业务审批意见、表单快照和审批审计不能只写入 Camunda 流程变量，也不能只依赖引擎的 history TTL。

# 业务人工任务表单

工作台 `/forms` 使用本地依赖的 Camunda form-js editor/viewer 2.1.1。此功能接入外部业务后端，首期覆盖人工任务；流程启动仍使用已有按节点字段及变量 JSON。

## 操作路径

1. 在“业务表单”新建草稿，填写稳定的 key 和名称。从左侧拖动字段到设计区，选择字段设置 label、key、校验及布局；窄屏在设计区横向滚动。切换“预览”查看办理效果。
2. “保存草稿”只保存定义，不发布。创建后的 key 不可改；保存失败保留编辑内容。关闭或离开未保存草稿时需要确认丢弃。
3. 点击“发布已保存草稿”并确认，生成后端返回的新版本。编辑已发布或已停用表单并保存后，主记录回到 DRAFT，旧发布快照保留。新绑定要求主记录是 PUBLISHED。
4. 在 `/workflow-designer` 选择审批或多人审批节点，从“业务表单”目录选择已发布版本。新选择写入 `bizFormKey: "form:<key>@<version>"`；清空选择则沿用流程级配置。导入、导出和撤销重做保留引用。
5. “生成 BPMN XML”或“发布任务模板”先检查表单当前状态和历史版本，再由后端编译/部署。启动实例后，在 `/workflow-business` 打开对应人工任务，修改回填数据，点击“提交表单并完成任务”。必填和格式错误阻止提交；成功后刷新任务列表。

“发布历史”提供快照预览及“回滚为新版本”。回滚从历史定义产生更大版本号，固定版本引用保持原快照；已有 `form:<key>` 和 `form:<key>@latest` 会读取历史最大发布版本。发布/回滚超时或连接中断时禁止重复写入并查询详情/历史，操作者核对后才解除锁定；版本增加本身不能证明原请求成功。

停用只改变业务目录状态，启用复用已有版本。删除只移除主记录，历史快照继续保留，同 key 重建后发布版本从历史最大值续增。这些操作不撤销已部署流程、不取消已有任务，也不自动改变固定版本引用。浏览已删除表单的历史尚无独立入口，可通过后端 history 接口查阅。

## 数据契约

| 位置 | 契约 |
| --- | --- |
| 业务模型人工节点 | `bizFormKey`，不复制 schema |
| 后端编译启动变量 | `{nodeId}_bizFormKey`，优先于流程级 `bizFormKey` |
| 旧 BPMN 表单字段 | `form` 独立编译为 `camunda:formKey`；选择业务表单不改写它 |
| 任务读取 | `GET /api/v1/tasks/{id}/bizForm` → `{type,data,values}` |
| 动态任务完成 | `POST /api/v1/tasks/{id}/complete` → `{variables:{fieldKey:{value}}}` |

viewer 校验并提取当前表单可提交字段，字段 key 就是变量名，不使用组件 id、不添加节点前缀、不提交全部实例变量。相同 key 表示共享变量；分支条件需要与字段 key 明确对齐，不自动推导 `params_rules`。多人审批场景需在表单中提供业务约定的 `vote` 字段，例如 `agree` / `reject`。

数组与对象作为原始 JSON 的 `value` 提交，由当前后端/Camunda 推断类型。实际环境中数组和对象都存为 `Object`，`bizForm.values` 返回原始 JSON；数字 12.5 存为 `Double`。当前引擎未配置 Spin `Json` 序列化器，显式 `type: "Json"` 会被拒绝，不能改回这一写法而不重新联调。

当前后端按字段 key 取值：本期对象回填实测使用有 key 的表达式字段。带 `path` 的嵌套 Group 需要后端按路径返回对应对象；实测 `details.note` 分组未回传父对象 details，尚不能保证这类分组的完整回填。使用普通无 path 分组或独立字段，复杂分组路径支持需后端补齐后再验收。

`route` 显示返回路径，本期不自动导航；`none` 显示通用无表单提示；未知类型或读取错误显示错误。后端将缺失引用、未知引用及缺失快照统一为 none，前端不据此猜测原因。折叠的“兼容办理与变量调试”保留原 `complete_biz` 与 variables 路径，与动态表单互斥提交。完成失败保留输入，建议先核对任务状态再重试。

表单 gateway 复用 `request()` 和既有代理认证/租户通道；设计器包只接收宿主数据源，不包含 API 或凭据。

## 可重复验收

本地行为检查运行 `pnpm test:forms`；`pnpm test` 还包含设计器选择/撤销/模型往返、网关、草稿及生命周期异常恢复检查。生产构建运行 `pnpm build`。

运行实际环境验收前启动 `pnpm dev`，配置现有 `/api`、`/api/camunda` 代理。脚本仅操作本次生成的唯一表单和流程，不输出认证信息：

```powershell
pnpm test:forms:integration
# 使用其他本地代理地址：
$env:FORM_SMOKE_BASE_URL = 'http://localhost:5171'
node scripts/form-smoke.mjs
```

脚本创建并发布表单、编译并发布专用流程模板、启动实例，检查两次审批及多人审批、原 key 变量提交与回填、固定/最新版本、回滚、停启用、route/none、删除快照保留和重建续增。请求使用实际表单 gateway 的变量包装逻辑。结果与 BPMN XML 写入 `.scratch/form-smoke/`。默认删除本次表单主记录、业务模板及专用引擎部署；业务表单历史和业务实例记录按后端规则保留。`--keep` 会保留专用资源，并额外启动一条浏览器验收实例；完成后按报告中的标识清理。
